01 — El mapa mental

Dos estructuras, una familia

Lo primero que hay que entender es que no hay dos implementaciones sueltas. Hay una familia: una clase abstracta con todos los algoritmos de lista escritos una sola vez, y dos subclases que sólo aportan la parte que depende de cómo se guarda el dato.

Es exactamente el reparto que hace el JDK con AbstractList → ArrayList / LinkedList. Copiar ese diseño no es trampa: es la respuesta correcta a «implementa una lista desde cero», porque demuestra que entiendes por qué el JDK lo tiene así y no es sólo que sabes escribir un array.

MyList<E>interface · extends java.util.List<E>
AbstractMyList<E>abstract · 444 líneas · todo el trabajo común
MyArrayList<E>Object[] · RandomAccess · 203 líneas
MyLinkedList<E>Node prev/next · Deque · 461 líneas
MySubList<E>vista que delega en la raíz · 119 líneas
La regla del paquete

Ninguna clase de collections/ puede usar java.util.ArrayList, LinkedList, Collections, Arrays ni HashMap para resolver su comportamiento.

Lo que sí se permite son las interfaces del JDK (List, Iterator, ListIterator, Deque, Comparator, RandomAccess), las excepciones (NoSuchElementException, IndexOutOfBoundsException, ConcurrentModificationException) y un puñado de utilidades de soporte (Objects, System.arraycopy, java.lang.reflect.Array).

Implementar las interfaces del JDK está permitido: lo que no se permite es delegar en sus implementaciones. Esa distinción es el centro de la prueba.

El orden de lectura

03 — Clase por clase

Qué hace cada una

MyList<E> — el marcador

collections/MyList.java

// 10 líneas. No añade un solo método.
public interface MyList<E> extends List<E> {
}

Existe por una razón práctica: que las firmas del servicio y de los DTOs digan «esto es una lista propia» y no «esto es un java.util.List cualquiera». No aporta comportamiento, pero hace la intención explícita en todo el código de arriba.

AbstractMyList<E> — el trabajo común

collections/AbstractMyList.java · 444 líneas

Es la clase importante. Contiene todos los algoritmos de lista que no dependen de cómo se almacena el dato, escritos una sola vez. Es lo que hace que dos implementaciones distintos no diverjan nunca.

Las 6 primitivas abstractasPor qué las necesita
size()Cuántos elementos hay
get(int)Leer una posición
set(int, E)Reemplazar una posición
add(int, E)Insertar en una posición
remove(int)Quitar por posición
listIterator(int)El iterador, que es distinto en cada estructura

Con esas seis se construye todo lo demás. Por ejemplo, indexOf no necesita saber cómo se guarda el dato: 

public int indexOf(Object o) {
    for (int i = 0; i < size(); i++) {
        if (Objects.equals(o, get(i))) {
            return i;
        }
    }
    return -1;
}

Y así clear(), addAll(), removeAll(), retainAll(), toArray(), toString() o sort() salen de aquí gratis para las dos estructuras.

MyArrayList<E> — sobre un array

collections/MyArrayList.java · 203 líneas

Sólo tres campos: el array de almacenamiento, el número de elementos ocupados y el contador de modificaciones. Todo lo demás son las seis primitivas. 

private Object[] elementData;   // array crudo: los genéricos no caben en un array
private int size;
private int modCount;       // lo lleva AbstractMyList

La inserción en medio es un desplazamiento de bloque con System.arraycopy, que es código nativo y por eso es mucho más rápido que un bucle: 

public void add(int index, E element) {
    checkPositionIndex(index);
    ensureCapacity(size + 1);
    int moved = size - index;
    if (moved > 0) {
        System.arraycopy(elementData, index, elementData, index + 1, moved);
    }
    elementData[index] = element;
    size++;
    modCount++;
}

Y el crecimiento de la capacidad, ×1.5 como en el JDK:

private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    // Crecimiento ×1.5, el mismo que usa java.util.ArrayList.
    int newCapacity = Math.max(oldCapacity + (oldCapacity >> 1), minCapacity);
    if (newCapacity == 0) { newCapacity = 1; }
    Object[] grown = new Object[newCapacity];
    System.arraycopy(elementData, 0, grown, 0, size);
    elementData = grown;
}
Detalle que suma puntos

oldCapacity >> 1 es la división por dos sin signo, y Math.max garantiza que la nueva capacidad nunca sea menor que la que hace falta. Si la capacidad llega a cero, el newCapacity == 0 la rescata: sin eso, grow crearía un array de tamaño 0 y add entraría en bucle infinito.

MyLinkedList<E> — sobre nodos

collections/MyLinkedList.java · 461 líneas

El nodo, con sus dos vecinos:

private static final class Node<E> {
    private E element;
    private Node<E> next;
    private Node<E> prev;
}

La diferencia con MyArrayList está en qué significa insertar. En el array hay que mover media lista; aquí hay que rehacer dos enlaces. 

private void linkLast(E element) {
    Node<E> created = new Node<>(element);
    if (last == null) {
        first = created;         // la lista estaba vacía
        last = created;
    }
    else {
        created.prev = last;
        last.next = created;
        last = created;
    }
}

Y la optimización que hace que get(i) no sea siempre igual de lento: se camina desde el extremo más cercano. 

private Node<E> node(int index) {
    checkIndex(index);
    Node<E> current;
    if (index < (size >> 1)) {        // primera mitad: desde first
        current = first;
        for (int i = 0; i < index; i++) { current = current.next; }
    }
    else {                                   // segunda mitad: desde last
        current = last;
        for (int i = size - 1; i > index; i--) { current = current.prev; }
    }
    return current;
}
La diferencia estructural que pide el enunciado

MyLinkedList implementa java.util.Deque entero: offer/poll para usarlo como cola FIFO, push/pop como pila LIFO, peekFirst, removeFirstOccurrence…

El enunciado de la entrevista dice exactamente esto: «LinkedList implementa Deque, así que puede usarse como una estructura FIFO estándar». Es la diferencia real entre las dos estructuras, y tenerla implementada es lo que separa una respuesta de principiante de una de senior.

MyListIterator<E> — el iterador fail-fast

collections/MyListIterator.java · 122 líneas

Comparte implementación entre las dos estructuras, así que recibe la lista como AbstractMyList y le pide lo que necesita. Tres campos: 

private final AbstractMyList<E> list;
private int expectedModCount;  // la foto del contador cuando nací
private int cursor;             // la posición siguiente
private int lastRet = -1;       // lo último devuelto, o -1

Y la comprobación que hace que el iterador sea fail-fast:

private void checkForComodification() {
    if (list.modCount() != expectedModCount) {
        throw new ConcurrentModificationException();
    }
}
El matiz que se pregunta

iterator.remove() y iterator.add() también incrementan modCount, así que después de mutar hay que actualizar expectedModCount a mano. Si no, el iterador se detectaría a sí mismo como «modificación concurrente» y el remove() normal del bucle reventaría.

Es un bug clásico al implementar iteradores, y está resuelto en remove() y add() del iterador.

MySubList<E> — la vista

collections/MySubList.java · 119 líneas

No copia nada. Guarda la lista raíz, el desplazamiento absoluto y el tamaño de la vista, y delega. Por eso el anidamiento funciona sin casos especiales: 

public E get(int index) {
    checkForComodification();
    checkIndex(index);
    return root.get(offset + index);     // la raíz, desplazada
}

public void add(int index, E element) {
    checkForComodification();
    checkPositionIndex(index);
    root.add(offset + index, element);
    size++;
    expectedModCount = root.modCount();   // yo también he modificado la raíz
}

ListType — el catálogo

collections/ListType.java · 79 líneas

Un enum con una fábrica por constante. Es lo que permite que el tipo de la lista vaya en la URL sin que el controlador conozca las clases concretas: 

public enum ListType {
    ARRAY_LIST { public <E> MyList<E> create() { return new MyArrayList<>(); } },
    LINKED_LIST { public <E> MyList<E> create() { return new MyLinkedList<>(); } };

    public abstract <E> MyList<E> create();
}
04 — Las decisiones que se preguntan

Seis puntos donde se decide tu nota

1. equals cruza implementaciones

«¿Por qué tu equals no comprueba que la otra lista sea del mismo tipo?»

public boolean equals(Object o) {
    if (o == this) { return true; }
    if (!(o instanceof List<?> other)) { return false; }
    if (other.size() != size()) { return false; }
    for (int i = 0; i < size(); i++) {
        if (!Objects.equals(get(i), other.get(i))) { return false; }
    }
    return true;
}

Porque en el JDK new ArrayList<>(List.of(1,2)).equals(new LinkedList<>(List.of(1,2))) es true. Comparar contra cualquier List replica ese comportamiento, y hace que una MyArrayList y una MyLinkedList con los mismos elementos sean iguales entre sí. Y como hashCode usa el algoritmo 31-based del JDK, dos listas iguales producen el mismo hash aunque sean de implementaciones distintas.

2. sort propio

«¿Por qué no usas Collections.sort?»

Porque está prohibido por la regla del paquete. El default de List.sort en el JDK delega en Arrays.sort, así que también está prohibido. Lo que queda es escribir un merge sort propio, y de paso estable. 

private static void merge(Object[] source, Object[] buffer, int low,
        int mid, int high, Comparator<?> comparator) {
    int left = low, right = mid, target = low;
    while (left < mid && right < high) {
        // "< 0" mantiene la estabilidad del merge sort.
        if (cmp.compare(source[right], source[left]) < 0) {
            buffer[target++] = source[right++];
        }
        else {
            buffer[target++] = source[left++];
        }
    }
    // ... se vacía el resto de los dos lados
}

3. Iteradores fail-fast

«¿Qué es modCount?»

Un contador de modificaciones estructurales. Cada mutación lo incrementa. El iterador guarda una foto al crearse y, si al avanzar el contador ha cambiado, lanza ConcurrentModificationException. Es una Best Effort: no garantiza nada, avisa de que el resultado sería impredecible. Es exactamente lo que hace el JDK.

4. subList es una vista, no una copia

«¿Qué pasa si modifico la lista original mientras tengo una vista?»

La vista queda obsoleta y la siguiente operación lanza ConcurrentModificationException. Es el mismo comportamiento que java.util.ArrayList.subList. Lo que sí funciona es mutar a través de la vista: el cambio se refleja en el padre, porque la vista delega en él.

5. La desviación de reversed()

«¿Por qué reversed() devuelve una copia y no una vista como en el JDK?»

Porque desde Java 21 java.util.List declara default List<E> reversed() y java.util.Deque declara default Deque<E> reversed(): mismo nombre, tipos de retorno incompatibles. Como MyLinkedList implementa las dos interfaces, el compilador no acepta el método por defecto de ninguna de las dos y hay que sobrescribirlo.

Lo podría haber resuelto con una vista invertida completa, como hace el JDK, pero eso exige duplicar la maquinaria de delegación. Devuelvo una copia invertida y el comportamiento es idéntico en las dos implementaciones. Es una desviación consciente, documentada en el javadoc, en el README y en el plan.

6. La lista vive en memoria

«¿Por qué ConcurrentHashMap y no una base de datos?»

Porque es una herramienta de demostración y entrevista, no un servicio de producción: lo interesante es poder crear una lista, mutarla paso a paso y ver el resultado. Y ConcurrentHashMap porque las peticiones HTTP llegan en paralelo.

    list.addAll(List.of("a", "b"));

Por qué esto importa más que los unit tests

Los unit tests son la red de seguridad interna. El endpoint es lo que le permite a quien evalúa comprobar el comportamiento sin leer una línea de código, que es justo lo que pedía el enunciado: «se puede exponer un endpoint para hacer la prueba».

06 — La capa web

Del HTTP a la lista

El camino de una petición es corto, y conviene poder recorrerlo de memoria:

HTTP  →  web/MyListController  →  service/ListService  →  collections/MyList<Object>
                                              ↓
                                    registro ConcurrentHashMap<String, StoredList>

La decisión de diseño de la capa web es que el tipo de implementación va en la URL: 

POST   /api/lists/arraylist      →  MyArrayList
POST   /api/lists/linked-list    →  MyLinkedList
GET    /api/lists/arraylist/{id}/elements/0

Para que quede explícito en la propia ruta qué estructura se está poniendo a prueba, que es exactamente lo que el entrevistador quiere contrastar. Y por eso ListType.parse() acepta arraylist, array-list y array_list sin distinguir mayúsculas.

index-of y contains son POST con cuerpo JSON y no GET con query param por una razón concreta: un query param siempre es texto, y para comparar con equals haría falta coercionar "1" a entero. Con JSON decide Jackson y la comparación es exacta.

07 — Defendiéndolo

En 60 segundos

Si te dejan un minuto para presentarlo, este es el guion:

  1. «Dos implementaciones, una familia»

    AbstractMyList implementa una sola vez todo lo que depende de get/set/add/remove; cada subclase sólo aporta seis primitivas. Igual que AbstractList en el JDK.

  2. «El array es contiguo; la lista enlazada, no»

    Acceso O(1) frente a O(n); inserción O(n) con desplazamiento frente a O(1) en los extremos. Y MyLinkedList añade Deque: cola y pila.

  3. «El contrato se cumple igual en las dos»

    equals cruza implementaciones, los iteradores son fail-fast y subList es una vista. Todo eso está en la base, una vez.

  4. «Y está demostrado, no afirmado»

    52 comprobaciones por HTTP, 84 tests, y un test diferencial que compara el comportamiento propio contra el del JDK tras cada una de 500 operaciones aleatorias.

Si te preguntan por lo que no hiciste

Menciona tú primero la desviación de reversed() y el que subList lanza ConcurrentModificationException ante cambios externos. Un candidato que conoce sus límites puntos de entrada mucho mejor que uno que presume de que todo está perfecto.
